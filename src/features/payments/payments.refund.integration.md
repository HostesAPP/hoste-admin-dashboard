# Transaction Table and Refund Preview

The provided screenshots define the table columns and Issue Refund layout. Full PRD v2.0 is not present locally. Existing `PaymentItem` and `RefundItem` contracts are preserved; new types are presentation snapshots, not invented database/API fields.

The table consumes `TransactionsAdapter.list` through the existing TanStack Query provider. Search, status, method, date, export, and pagination use the same filtered source. Mock reporting ends September 18, 2026, rather than using today's date against historical fixtures. Totals reflect actual fixture rows rather than the screenshot's fictional 154-record count. Existing header/cards and their data remain unchanged. First three transaction entities reuse existing payments; additional rows only extend preview data. Retry checks eligibility and reports that no gateway operation occurred; it does not fabricate status transitions.

The shared `BOOKINGS_DATA` fixture is the source of payment details, payer email, booking relationship, and payment method. `MOCK_PAYMENTS` and `MOCK_TRANSACTIONS` are projections of that source, not separate payment fixtures. Both `/bookings/[id]/payments` and `/payments/[id]/refund` load the same refund context on the server; the adapter accepts a payment ID, booking ID, or display booking reference. `/payments/[id]` redirects to the canonical booking payment page. `data/refunds.data.ts` contains only refund-specific available-balance snapshots, allowed reasons, and policy copy, while `MOCK_REFUNDS` contains historical refund records linked by payment ID. There is no separate `MOCK_REFUND_CONTEXTS` dataset. Replace the mock loader with an authorized server data-access function, and the injectable refund adapter's `quote`/`review` with backend operations when the approved contract is available. Never call a money-transfer API directly from presentation components.

RHF/Zod validate positive amounts with at most two decimal places, the backend-supplied available balance, selected reasons, and 250-character admin notes. Eligibility is checked again by the mock adapter. The balance and fee/net summary are supplied by snapshots/quotes, not a frontend policy calculation. The screenshot's 2.9% fee is not treated as an approved business rule: mock quotes use zero processing fee to match the existing RefundItem fixture. Production amounts/fees, authorization, concurrency, idempotency, status transitions, notifications, and audit records belong to the backend.

Original Payment Method is the only permitted destination under the existing contract. The wallet choice shown in the screenshot is disabled. Reasons and policy wording are preview configuration and require product/backend confirmation. Booking image and host count remain unavailable because the source booking does not provide them; the UI uses an image placeholder and does not invent a count or event time. Historical refund records have no status field, so history shows "Status unavailable" rather than claiming completion. No real refund is issued, no historical balance is mutated, and no synthetic audit or refund records are created by review confirmation.

Missing related bookings and empty history are displayed explicitly. Read-only/unavailable refund eligibility disables form submission. Table actions have accessible names and hover descriptions, and desktop layout is verified at 1280px and larger.

Each transaction comes from its owning booking, preserving its payment ID, reference, amount, fees, status, and timestamp. The mock filter period ends on the latest booking payment date so the existing default date filter includes the fixtures. Rows and transaction reference links open `/bookings/[id]/payments`; eye, retry, and refund actions do not trigger row navigation. A production adapter must supply booking relationships, payment-method metadata, and action eligibility from the backend. The payment details page displays recorded service and processing fees rather than calculating a commission; escrow balances, payout dates, card numbers, and unsupported activity events are not manufactured.

Review uses the screenshot's two-column dialog, with immutable submitted draft and quote values. Busy confirmation blocks dismissal and duplicate clicks; errors remain in the dialog. The adapter returns receipt metadata rather than the UI manufacturing a successful gateway reference. Mock receipts use a PREVIEW-prefixed reference and explicitly report that delivery was not submitted. No completed refund or audit record is created.

The success dialog opens a receipt viewer with Print and Save PDF controls. Save PDF uses `pdf-lib` and its Unicode font engine, with locally bundled DejaVu fonts and their upstream license notice. The PDF is generated from the same authoritative receipt snapshot as the viewer, with theme colors read from the project tokens. Print uses a separate, text-escaped HTML document. Admin-only notes are excluded from both output formats.

The receipt includes a prominent preview-only disclaimer. It does not invent a customer ID, authorized staff member, processed status, gateway transaction reference, or fee percentage. A production adapter should return authoritative gateway status and receipt data; only that response should determine initiated/success wording and delivery estimates. Receipt generation does not include credentials or send anything to a customer.
